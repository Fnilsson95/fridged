# fridged: v1 data model

A barcode scanner next to the fridge plus a web app. Items are scanned IN after shopping and OUT when started. The app shows what was spent, what was used, the gap between them, and the current stock.

This document describes the **v1 database**: two tables, kept deliberately small. Everything else is added later with migrations (see [Deferred](#deferred-to-later-versions)).

## Principles

- **A barcode identifies a product, not a single item.** Every bottle of the same Coca-Cola 0.5 L has the same barcode. Two scans of the same barcode means stock of 2.
- **Money is integer öre.** Stored and sent over the API as integers. The UI shows SEK (`12,50 kr`) and accepts `12,50` or `12.50` as input.
- **Timestamps are UTC ISO-8601 strings.** Stockholm time is used only to decide reporting periods (weeks and months).
- **Events are append-only.** Nothing is deleted. An undo sets `reverted_at`.
- **Stock and totals are computed, not stored.** There is no `stock` column, so the numbers cannot drift out of sync.
- **All business rules live in the backend.** The device daemon never touches the database.

## Tables

### `products`

One row per barcode.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER PK | no | |
| `barcode` | TEXT UNIQUE | no | Normalized GTIN, stored as text to keep leading zeros |
| `name` | TEXT | no | From Open Food Facts, editable. Fallback: `Unknown <barcode>` |
| `brand` | TEXT | yes | |
| `size_label` | TEXT | yes | Display only, e.g. `500 g`, `1 l` |
| `image_url` | TEXT | yes | |
| `current_price_ore` | INTEGER | yes | NULL means the product needs a price. CHECK >= 0 |
| `created_at` | TEXT | no | First time the barcode was seen |
| `updated_at` | TEXT | no | Last change to the row |

### `events`

A log of every scan. Never edited or deleted.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | INTEGER PK | no | |
| `client_event_id` | TEXT UNIQUE | no | UUID generated by the device, makes retries idempotent |
| `product_id` | INTEGER FK | no | References `products(id)` |
| `type` | TEXT | no | `in`, `out` or `stocktake` |
| `unit_price_ore` | INTEGER | yes | Price snapshot at scan time, NULL until the product is priced |
| `occurred_at` | TEXT | no | When the item was scanned (device clock, UTC) |
| `received_at` | TEXT | no | When the backend received it (UTC) |
| `reverted_at` | TEXT | yes | Set when the event is undone |

Suggested indexes: `(product_id, occurred_at)` and `(type, occurred_at)`.

### Draft DDL

```sql
CREATE TABLE products (
  id                INTEGER PRIMARY KEY,
  barcode           TEXT    NOT NULL UNIQUE,
  name              TEXT    NOT NULL,
  brand             TEXT,
  size_label        TEXT,
  image_url         TEXT,
  current_price_ore INTEGER CHECK (current_price_ore IS NULL OR current_price_ore >= 0),
  created_at        TEXT    NOT NULL,
  updated_at        TEXT    NOT NULL
);

CREATE TABLE events (
  id              INTEGER PRIMARY KEY,
  client_event_id TEXT    NOT NULL UNIQUE,
  product_id      INTEGER NOT NULL REFERENCES products(id),
  type            TEXT    NOT NULL CHECK (type IN ('in', 'out', 'stocktake')),
  unit_price_ore  INTEGER CHECK (unit_price_ore IS NULL OR unit_price_ore >= 0),
  occurred_at     TEXT    NOT NULL,
  received_at     TEXT    NOT NULL,
  reverted_at     TEXT
);

CREATE INDEX ix_events_product_time ON events (product_id, occurred_at);
CREATE INDEX ix_events_type_time    ON events (type, occurred_at);
```

The SQLAlchemy models and Alembic migrations are the source of truth for exact types and constraints. This DDL is a reference sketch.

## Scan modes

| Mode | Creates | Returns to OUT after |
|---|---|---|
| OUT (default) | `out` event | |
| IN | `in` event | 120 s |
| STOCKTAKE | `stocktake` event (first fill, not counted as spending) | 10 min |

Command cards (Code 128) are handled locally by the daemon: `FT:MODE:OUT`, `FT:MODE:IN`, `FT:MODE:STOCKTAKE`, `FT:UNDO`.

Scan results: `stocked`, `stocktaken`, `used`, `new_item`, `not_in_stock`, `duplicate`.

- `new_item`: the barcode was unknown, so a product was created (name lookup via Open Food Facts, otherwise `Unknown <barcode>`), and the event is recorded.
- `not_in_stock`: an OUT scan while stock is 0. **No event is recorded**, so "used" is never inflated.
- `duplicate`: a `client_event_id` the backend has already processed. Nothing new is recorded.

## What is computed from these tables

Only non-reverted events (`reverted_at IS NULL`) count.

| Value | Definition |
|---|---|
| Stock (per product) | number of `in` + `stocktake` events minus number of `out` events |
| Spent | sum of `unit_price_ore` over `in` events |
| Used | sum of `unit_price_ore` over `out` events |
| Gap | Spent - Used |
| Needs price | products where `current_price_ore IS NULL` |
| History | the events list, newest first, with undo |

`stocktake` events add to stock but are never part of Spent or Used. Events without a price (`unit_price_ore IS NULL`) are excluded from totals until the product is priced.

### Setting a price

In one transaction:

1. Update `products.current_price_ore` and `updated_at`.
2. Backfill `unit_price_ore` on that product's events where it is NULL (for `stocktake` events it stays NULL).

Changing an existing price affects **future** events only. Old events keep their snapshot, so past totals never change.

## Barcode normalization

Done in one backend function, so the device and web app always agree:

1. Strip whitespace and keep digits only.
2. A 12-digit UPC-A gets a leading `0` (GTIN-13). EAN-8 stays 8 digits.
3. Verify the check digit. An invalid digit is logged as a warning but the scan is still accepted.

## Multipacks

A multipack barcode on the outer wrapper is treated as **one unit**. Scanning OUT means "opened". The individual items inside are not tracked.

## Deferred to later versions

All of these can be added without losing or redoing data, because events are append-only and everything is computed from them.

| Feature | How it is added later |
|---|---|
| Expiry dates, days in fridge, oldest-first usage | A `stock_items` table (one row per package), filled by replaying events |
| Shopping list and `min_stock` | New `shopping_items` table plus a nullable `products.min_stock` column |
| Price history and chart | New `price_history` table (old totals are already protected by event snapshots) |
| Emailed weekly/monthly reports | New `report_runs` table, reports computed from events |
| Settings, archiving products, event source and notes | New table or columns when needed |
| Multiple barcodes per product | A `product_barcodes` table |
| Categories | A nullable `products.category` column |
